# Backend defects found while rebuilding the web app

Found while building the web app against the live API. Each row says what
was fixed and where. Rows 19 to 24 were found while fixing the first
eighteen; #7 and #10 were product decisions and are recorded with the
decision taken.

## Fixed

| # | Area | Defect | Fix |
|---|------|--------|-----|
| 1 | Domains | Reads addressed by **slug** resolved the domain but ran child queries with the slug, so senders and reports came back empty. | `sender.controller`, `report.controller`, `domain-scan.controller` (list), `forensic.controller` (list) and `onboarding.service` (`assessPolicyReadiness`) pass the resolved `domain.id`. |
| 2 | Billing | The billing-portal return URL was `${BETTER_AUTH_URL}/app/billing`: the API's origin and a path the app never had. | `billing.controller` returns to `${APP_URL}/billing`. The web `/app/billing` → `/billing` redirect stays for sessions and emails issued before the fix. |
| 3 | Billing | `PATCH /billing/plan` to MOORING cancelled outside the `try`, so `NO_SUBSCRIPTION` escaped as a 500. | The cancel runs inside the `try` and answers the 409. |
| 4 | Billing | `PATCH /billing/plan` always answered `scheduled` / `cycle_end`, though Paddle applies at once. | `changePlan` returns `effectiveAt: immediate \| cycle_end` and `effectiveDate`; the controller answers `status: applied \| scheduled` with the date. The web reads `status`. |
| 5 | Billing | The grace length was not exposed and `graceEndsAt` was never written, so `GET /billing` said `graceEnds: null` during a running grace. | `dunning.ts` adds `graceEndFor` (period end + `dunningGraceDays`) and stores `graceEndsAt` with the WARNED claim. `billingStatus` returns `graceEnds` (stored, or computed while past due) and `graceDays`. |
| 6 | Billing | No endpoint returned quota usage. | `GET /entitlements` adds `usage: { client, activeDomain, member }` from `quotaUsage`. Billing shows exact counts when present and keeps the "up to" wording only as a fallback. |
| 8 | Portal | `GET /api/portal` did not select domain `slug`. | Selected; portal links use the slug, falling back to the id. |
| 9 | Portal | A contact invited by several workspaces got a bare `400 … Pass organizationId`. | `portal.middleware` answers `400 CHOOSE_WORKSPACE` with `workspaces: [{ organizationId, name, clients }]`, and `403` for a workspace the contact holds no grant in. `/portal` shows a chooser and carries `?org=` through the domain pages. |
| 11 | Portal | `possibleSpoofingSources[].detail` was operator prose ("Confirm with the domain owner, then enforce") sent to the domain owner. | `GET /api/portal/domains/:id` replaces `detail` with a sentence for the client. The operator's endpoint is unchanged. Asserted in `portal.integration.test.ts`. |
| 12 | Config | `npm run dev` in `apps/api` refused to start without `NODE_ENV=development` set by hand. | `scripts/dev.mjs` sets it for the dev process. `env.ts` still treats an unset `NODE_ENV` as production, on purpose. |
| 13 | Plans | 402 messages opened with the raw entitlement key ("auth.sso is not included in Harbor"), and the quota refusal always quoted the active-domain limit. | `plan-catalog.ts` exports `entitlementLabels`, used in the message. The quota refusal quotes the limit of the quota actually hit. `planRefusalText` in the web stays as a fallback. |
| 14 | Slack | Errors were `{ error: "message", code }`, unlike every other route; non-boolean `enabled` and unbounded labels were accepted. | Nested `{ error: { code, message } }`; inputs validated (`enabled` must be boolean, `channelLabel` trimmed to 80). |
| 15 | Members | Inviting someone sent no email. | `sendInvitationEmail` queues `workspaceInvitationEmail`, linking to `${APP_URL}/welcome`, where pending invitations are listed with Join and Decline (also above the portfolio). |
| 16 | API keys | Every key route, including the list, needed `billing:update` (owner only). | List and revoke need `organization:update` (owner and admin). Issuing keys and deleting revoked ones stay owner-only. The page and the role table say so. |
| 17 | SSO | No way to switch a connection off or change who it admits. | `PATCH /workspaces/:id/sso-connections/:connectionId` (enabled, label, allowed domains, provisioning, default role; strict schema; same allowlist rule as creation), audited as `SSO_CONNECTION_UPDATED` (migration `20261023120000_sso_connection_updated`). The SSO page has an on/off switch and an edit form. Documented in `openapi.ts`. |
| 18 | Erasure | The preview said aggregate reports would be deleted with the reason "Retained as security evidence". | A `delete` row carries no retention reason. The erasure statement, certificate and OpenAPI text now say what happens: everything in scope is deleted, including DMARC reports and forensic samples; audit and billing records are kept with identifying fields cleared. |
| 19 | Email | Emailed links (billing, domain, portal, export download, erasure cancel, trust centre) were built from `BETTER_AUTH_URL`, the API's origin, and some pointed at paths the app does not have. | `mailer.ts` builds from `APP_URL` with the app's real paths (`/billing`, `/domains/:id`, `/portal`, `/settings/erasure`). |
| 20 | Email | The payment-failed email gave a grace end of "now + 7 days", which matched neither the setting nor what billing showed. | It uses `graceEndFor`, the same date stored and shown on the billing page. |
| 21 | Email | Dates appeared as raw ISO strings. | `readableDate()` in `templates.ts` (en-GB, UTC) formats every date. |
| 22 | Email | The plan-changed email promised "at the end of the period you have already paid for" and "no mid-cycle amount" for Paddle changes, which apply at once and prorate. | `planChangedEmail` takes `timing`; the immediate version says the plan is live and the provider adjusts the charge. Doc comments in `checkout.service` and `paddle.provider` and the OpenAPI text for `PATCH /billing/plan` corrected. |
| 23 | OpenAPI | The new SSO `PATCH` route was undocumented (caught by `openapi.test.ts`). | Documented. |
| 24 | Auth | Session reads (`get-session`, the organization and invitation lists) shared the sign-in limit of 20 a minute per address. The web app reads the session on every server render, so about twenty page views in a minute made the next sign-in answer 429. Found by the clickthrough. | `createSessionReadRateLimiter` gives those GETs their own bucket at the workspace-route budget (600 a minute). Sign-in, sign-up, password reset and `verify-email` stay on the strict limit. Asserted in `postgres-rate-limit-store.integration.test.ts`. |

## Decided and fixed (were product decisions)

| # | Area | Question | Decision and fix |
|---|------|----------|------------------|
| 7 | Plans | `dataRetentionDays` only decided which domains count as active, and `auditRetentionDays` was read by nothing. Neither was enforced as retention. | **Retention is the same on every plan.** Tiered retention would delete or hide a customer's history on downgrade, behind a window the product does not publish. Retention is set per deployment by data class (`REPORT_RETENTION_DAYS`, `FORENSIC_RETENTION_DAYS`, `FORENSIC_PII_RETENTION_DAYS`; the audit log is kept indefinitely as evidence), and the Trust Center and compliance pack already publish those windows. Plans differ by quotas and features. `dataRetentionDays` is renamed `activeDomainWindowDays` (values unchanged, so quotas behave the same), and `auditRetentionDays` is removed. The erasure certificate now records the enforced report retention instead of the plan figure. A unit test refuses any retention-shaped field on a plan. |
| 10 | Portal | The portal read routes had no plan check; `portal.client` was checked only when a grant was created. | **Gate the feature where it is used, and keep the data.** Downgrades are usually handled this way: the feature stops, the setup is kept, and an upgrade restores it. `requirePortalScope` checks `portal.client` on every portal read (overview, domain and branding) and answers `403 PORTAL_PAUSED` with `workspaceName`. Grants are not touched, so the agency can still list and revoke them, and an upgrade brings the report back. The contact sees "This report is paused" naming the provider, never a plan or price. Settings → Client portal tells the agency what their contacts see. Covered in `portal.integration.test.ts`; documented in `openapi.ts`. |

Nothing is open.
